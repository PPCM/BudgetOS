# Changelog - 2026-05-01

## Summary
Fixed a critical bug where the hourly scheduler was creating duplicate occurrences of recurring transactions on the day of execution. Added an admin maintenance UI to detect and clean up the duplicates already created in production.

## Changes

- [src/models/PlannedTransaction.js] Replaced calculateNextOccurrence(pt) with advanceNextOccurrence(pt) inside createOccurrence: previously next_occurrence was recomputed from startDate and could return today's date, making the cron re-trigger every hour. New method advances by one frequency period from the current next_occurrence; returns null for once or when next > endDate
- [src/services/duplicateService.js] Created service to detect and clean up duplicate recurring transactions: groups by (user_id, recurring_id, date), keeps reconciled or oldest, deletes the rest via Transaction.delete to recompute account balances
- [src/controllers/adminController.js] Added previewRecurringDuplicates and cleanupRecurringDuplicates handlers
- [src/routes/admin.js] Added GET /admin/duplicates/recurring (preview) and POST /admin/duplicates/recurring/cleanup
- [client/src/lib/api.js] Added previewRecurringDuplicates and cleanupRecurringDuplicates to adminApi
- [client/src/pages/AdminSettings.jsx] Added Maintenance card with Analyze + Cleanup buttons, preview table, confirmation dialog, query invalidation for transactions/accounts/dashboard
- [client/src/locales/{fr,en,de,es,it,pt,ru,sv,zh}.json] Added admin.duplicates.* keys (title, subtitle, analyze, cleanup, confirmCleanup, cleanupSuccess, noDuplicates, found, col.*)
- [tests/models/PlannedTransaction.test.js] Added 4 tests for createOccurrence covering: today advances next_occurrence, hourly scheduler safety, once returns null, end_date boundary returns null
- [tests/integration/adminDuplicates.test.js] Created 18 integration tests covering preview/cleanup auth, detection across user isolation, reconciled-transaction preservation, balance recalculation, idempotency, CSRF protection
- [src/models/Account.js] Replaced single delete() that did soft-or-hard with three explicit operations: deactivate() (reversible, pauses linked planned transactions), reactivate() (does not auto-resume planned transactions), delete() now refuses an active account and hard-deletes when inactive (cascades transactions/splits/recurring via FKs). Added findAnyByIdOrFail() to operate on inactive rows
- [src/controllers/accountController.js] Added deactivateAccount + reactivateAccount handlers
- [src/routes/accounts.js] Added POST /accounts/:id/deactivate and /reactivate
- [src/validators/accounts.js] Added includeInactive query param so the Accounts page can fetch both active and inactive accounts
- [client/src/lib/api.js] Added accountsApi.deactivate/reactivate; getAll now accepts params (used to pass includeInactive=true)
- [client/src/pages/Accounts.jsx] Split rendering into active section + dimmed Deactivated section. Active card actions: Edit + Deactivate (window.confirm). Inactive card actions: Reactivate + Permanent Delete (typed-name confirmation modal with explicit warning of cascading deletes). Wired query invalidation to transactions/dashboard/projections
- [tests/models/Account.test.js] Replaced soft-delete tests with the new three-state behavior (refuse-active, hard-delete-inactive, cascade transactions, deactivate pauses linked PT, reactivate keeps PT paused, idempotency)
- [tests/integration/accounts.test.js] Added Deactivate/Reactivate suite + reworked delete tests to cover the new "must be deactivated first" rule, includeInactive listing, and CSRF/cross-user protection
- [client/src/locales/{fr,en,de,es,it,pt,ru,sv,zh}.json] Added accounts.deactivate/reactivate/permanentDelete + warning modal copy

## Notes
- Production had duplicates because the cron ran every hour and next_occurrence stayed equal to today after each createOccurrence
- Cleanup uses Transaction.delete (not raw DB delete) so account balances stay correct
- A reconciled duplicate (already matched to a bank statement) is preferred over the oldest when both exist in a group
- Account hard-delete cascades transactions/splits/planned_transactions via FK ON DELETE CASCADE; the new two-step flow forces the user to deactivate first to make the destructive intent explicit
